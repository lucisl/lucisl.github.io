面试题库 / 002 / 活动 / 奖励一致性

ACTIVITY / REWARD

奖励一致性

奖励不是发个奖，是资金一致性。

一句话

活动奖励不是"发个奖"，是资金一致性：重复发是资损，漏发是投诉；要靠唯一键、流水、状态机、回收队列、对账兜住。

1. 奖励状态机：先记账，再发奖

奖励从"配置"到"到账"要经过：

配置 → 触发 → 受理（PENDING） → 发放（SUCCESS / FAILED）
                                      ↓
                                 重试 / 死信 / 人工补偿

关键原则

  • 先记账，再发奖：流水是事实，发奖是动作。
  • 每次发放有唯一业务键：order_no / trans_no。
  • 失败可重试，重试不重复发。
  • 已发可回收：canRevert + 回收队列。
  • 状态机：PENDING 可重试，SUCCESS 不可重复，FAILED 进补偿。

2. GET / USE 双流水

以魔盒赐福 BoxBlessService 为例：

  • GET：发放流水，trans_no = 队列 order_no。
  • USE：核销流水，trans_no = 送礼批次号。
  • 发放：先插 GET 流水，唯一键冲突 = 已发放，直接返回；再插用户券（ACTIVE）。
  • 核销：UPDATE ... WHERE status='ACTIVE' 单行原子，并发不会双消；成功后写 USE 流水。

为什么双流水

  • 能查"发了多少、用了多少、剩多少"。
  • 发放和核销解耦，退款 / 回收 / 对账都有据可查。
  • 唯一键兜底幂等，不依赖"先查后写"。

代码要点

  • trans_no 唯一键是幂等闸门；DuplicateKeyException 直接按成功处理。
  • 发放在一个本地事务内：流水 + 用户券要么都成功，要么都回滚。
  • 核销用条件更新，不用"先 select 再 update"。
  • 配置缺失 / 奖池不匹配：飞书告警 + 队列标记失败，不静默吞掉。

设计亮点

  • 流水和状态分离：GET/USE 是事实，券状态是当前状态。
  • 幂等闸门是数据库唯一键，不是 Redis / 应用判断。
  • 事务边界清晰：发放一个事务，核销一个条件更新。

3. 宝箱多级结算：唯一键 + 状态机 + Redis 标记

GameBoxAwardHandler / GameBoxRankHandler：

  • 奖励记录先 insert，唯一键冲突 = 已处理。
  • 状态：PENDING → SUCCESS / FAILED。
  • 榜单累计：orderNo + "_" + level，一笔流水跨多级也幂等。
  • 日榜 / 总榜结算：Redis 标记防重；异常时删除标记，允许后续补偿。

难点

  • 多级奖励：同一个 orderNo 要发多个等级，不能因为唯一键把后续等级挡掉 → 加 level 后缀。
  • 结算失败：不能把标记永久留着，否则永远补不了 → 失败删标记。
  • 状态机：PENDING 是"已受理未完成"，FAILED 可重试，SUCCESS 不可重复。
  • 并发结算：Redis 标记 + 唯一键双保险；标记是"快速防重"，唯一键是"最终事实"。

设计取舍

  • 先插记录再发奖：记录是幂等闸门；发奖失败更新状态，不重复插。
  • Redis 标记 vs DB 唯一键：Redis 快，DB 稳；两者一起用。
  • 失败删标记 vs 人工重试：自动补偿优先，人工兜底。

4. 捕鱼：条件更新 + 唯一索引 + 溢出伤害

GoldenFisheryFishHandler：

  • 扣血：UPDATE ... WHERE id=? AND status='ALIVE'，影响行数=0 说明并发/已死，放弃。
  • 捕捞成功：再用 WHERE status='ALIVE' 抢"捕捞处理权"，防重复结算 / 重复发奖。
  • 刷鱼：唯一索引保证一个房间只有一条活鱼；DuplicateKeyException / DeadlockLoserDataAccessException 后重查。
  • 溢出伤害：一条鱼被打死，剩余伤害递归打新鱼；orderNo 加 _depth 后缀，保证每条鱼的榜单流水幂等。
  • 异步：血量变化 / 广播用 CompletableFuture，失败不影响主流程。

为什么不用分布式锁

  • 条件更新 + 唯一索引已经能抢处理权；锁只增加复杂度和失败点。
  • 死锁 / 唯一键冲突是预期内的，捕获后重查即可。

设计亮点

  • 状态机 ALIVE → CAUGHT 用条件更新推进，天然防并发。
  • 溢出伤害用 orderNo_depth 解决"一笔流水打多条鱼"的幂等。
  • 唯一索引解决"一房间多活鱼"的并发插入。

5. 奖励回收 / 补偿

AwardHandler.revert() + GiftAwardRevertQueue：

  • 发放记录带 canRevert。
  • 回收走独立 gift_award_revert_queue，不和正常发奖抢资源。
  • 回收失败可重试 / 告警 / 人工补偿。

使用场景

  • 等级变化：用户等级降了，之前按高等级发的奖励要回收。
  • 活动回滚：活动配置错了，已发奖励要撤回。
  • 风控：异常账号的奖励要冻结 / 回收。

原则

  • 回收是"另一条链路"，不要阻塞发奖。
  • 回收也要幂等：同一奖励不能回收两次。
  • 回收要有审计：谁、什么时候、为什么回收。
  • 回收和再发要区分：回收后重新发，要有新的业务流水号。

6. 对账与巡检

三方对账

  • 配置：活动应该发什么。
  • 榜单：谁应该得。
  • 发奖记录：实际发了什么。

巡检

  • PK 活动按阶段跑 .check.ts：查 mod_common_round 状态、榜单、奖励配置、mod_common_award_record。
  • 差异输出：少了哪些 rank / 奖励类型 / 发放对象。
  • 异常转缺陷 / 工单，人工补偿。

指标

  • 发放成功率、失败率、重试次数、回收次数。
  • 资损金额、差异条数、对账覆盖率。
  • 发奖延迟、PENDING 堆积、FAILED 堆积。

设计亮点

  • 配置 / 榜单 / 发奖记录三方对账，能定位"该发没发 / 发错对象 / 重复发"。
  • 巡检脚本化、定时化，活动阶段自动抽检。
  • 异常转单，人来决定补偿/回收。

7. 失败模式

失败点 后果 兜底
重复消息 / 重复请求 重复发奖 唯一键 / 流水号
发奖成功、状态更新失败 状态不一致 状态机 + 对账
多级发奖中途失败 部分等级漏发 orderNo_level + 重试
回收失败 该回收没回收 回收队列 + 告警
Redis 标记残留 永远不能重试 失败删标记
配置缺失 / 奖池不匹配 发错奖 / 发不出 配置校验 + 飞书告警
DB 事务回滚、Redis 已更新 缓存不一致 sync / 对账重建

8. 设计亮点总结

  1. 流水先行：先插流水再发奖，唯一键做幂等闸门。
  2. GET/USE 双流水：发放、核销、余额三方可查。
  3. 状态机：PENDING/SUCCESS/FAILED，可重试、可补偿、不可重复。
  4. 条件更新：核销 / 捕鱼用 WHERE status=... 单行原子，防并发双消。
  5. 多级幂等：orderNo + "_" + level 支持一笔流水跨多级。
  6. 回收队列：发放/回收分离，不阻塞主链路。
  7. 三方对账：配置 / 榜单 / 发奖记录，能定位资损。
  8. 巡检闭环：脚本化、定时化、异常转单。

9. 边界 / 坑

  • 唯一键粒度要设计好：trans_no 太粗会挡掉合法多次发放，太细会重复。
  • 状态机要闭合：PENDING 不能永久停留，要有超时 / 补偿。
  • Redis 标记和 DB 唯一键要一致；只靠 Redis 会丢，只靠 DB 会慢。
  • 回收和再发要有新的流水号，不能复用旧 trans_no。
  • 配置变更 / 奖池调整要能对账；历史发奖记录不能被配置覆盖。
  • 多级奖励的 level 后缀要稳定；不能因为顺序变化导致幂等失效。

10. 面试怎么讲

30 秒版

奖励一致性靠三件事：先插流水，trans_no 唯一键做幂等；核销用 UPDATE ... WHERE status='ACTIVE' 条件更新；失败走回收/补偿队列，定时对账。多级奖励用 orderNo_level 保幂等，结算用 Redis 标记防重，失败删标记允许补偿。

2 分钟版

我们把奖励拆成"流水 + 状态 + 动作"：GET/USE 双流水记录发放和核销，唯一键做幂等闸门；发放在本地事务内，核销用条件更新；宝箱多级结算用 orderNo_level 和状态机，Redis 标记防重、失败删标记；捕鱼用条件更新抢处理权、唯一索引防重复刷鱼、溢出伤害用 orderNo_depth；回收走独立队列，最后用配置/榜单/发奖记录三方对账。

追问：怎么防重复？

唯一键 + 流水号；先插流水再发奖，DuplicateKey 就是已发放。核销用条件更新，不用先查后写。

追问：怎么定位资损？

配置 / 榜单 / 发奖记录三方对账；先止血（关活动/关发奖），再按流水和 trace 定位，最后补偿/回收。

追问：这个设计有什么问题？

唯一键粒度、状态机闭合、Redis 标记与 DB 一致、多级 level 稳定、回收与再发流水号，都是要治理的点。

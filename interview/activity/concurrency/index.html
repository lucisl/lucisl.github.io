ACTIVITY / CONCURRENCY

高并发玩法

条件更新、唯一索引、锁、缓存分层与事件驱动。

一句话

活动高并发不是"加机器"，是状态机 + 条件更新 + 唯一索引 + 锁 + 缓存分层 + 事件驱动一起用，保证不重、不丢、不拖垮。

1. 捕鱼：条件更新 + 唯一索引 + 溢出伤害

场景

  • 一个房间一条活鱼，用户送礼打鱼；鱼血归零后结算，溢出伤害继续打新鱼。

状态机

ALIVE → (血量归零) → CAUGHT
  ↑                    │
  └── 刷新新鱼 ←───────┘

并发点

  • 多个用户同时打同一条鱼。
  • 鱼死瞬间多个请求同时触发结算。
  • 一条鱼死后，剩余伤害要打新鱼。
  • 新鱼刷新时多个请求同时插入。

解法

  • 扣血：UPDATE ... WHERE id=? AND status='ALIVE'，影响行数=0 放弃。
  • 捕捞：再用 WHERE status='ALIVE' 抢"捕捞处理权"，只有一个请求能成功。
  • 刷鱼：唯一索引保证一房间一活鱼；DuplicateKey / Deadlock 后重查。
  • 溢出：递归打新鱼，orderNo 加 _depth 后缀，保证多条鱼流水幂等。
  • 异步：血量变化 / 广播用 CompletableFuture，失败不影响主流程。

为什么不用分布式锁

  • 条件更新 + 唯一索引已经够，锁增加失败点。
  • 死锁是预期：捕获后重查，不当作系统错误。
  • 数据库行锁在单行竞争下比 Redis 锁更直接。

设计亮点

  • 状态机用条件更新推进，天然防并发。
  • 唯一索引解决"一房间多活鱼"。
  • orderNo_depth 解决"一笔流水打多条鱼"的幂等。
  • 异步副作用不阻塞主流程。

坑

  • 溢出递归深度要限制，避免一条超大神豪礼物打穿很多鱼。
  • 唯一索引冲突/死锁重查要有限制，避免活锁。
  • 异步消息失败只记录，重要广播要补偿。

2. 宝箱 / 赐福：唯一键 + 状态机

宝箱

  • 奖励记录先 insert，唯一键冲突 = 已处理。
  • PENDING → SUCCESS / FAILED；失败可重试。
  • 多级结算：orderNo + "_" + level。
  • 结算标记 Redis 防重；失败删标记，允许补偿。

赐福券

  • GET 流水 trans_no = order_no；USE 流水 trans_no = 批次号。
  • 核销 UPDATE ... WHERE status='ACTIVE' 单行原子。
  • 发放在本地事务内：流水 + 券一起成功 / 失败。

设计亮点

  • 唯一键是幂等闸门，不是"先查再写"。
  • 状态机让失败可重试、成功不可重复。
  • Redis 标记是快速防重，唯一键是最终事实。

坑

  • 状态机要闭合：PENDING 不能永久停留。
  • Redis 标记失败要删，否则永远补不了。
  • 多级 level 后缀要稳定。

3. 余额单写者锁

lita-payment 的 UserBalanceLockAspect：

  • @UserBalanceLock + Redisson RLock。
  • tryLock(waitMs, leaseMs)；leaseMs<=0 用看门狗续期。
  • 获取失败：failFast 抛"系统繁忙"，否则降级直连 DB。
  • 释放判断 isHeldByCurrentThread()；过期 / 释放失败记指标。
  • 按 biz + userId 判断是否在锁范围，不是所有交易都加锁。
  • 指标：等待时长、获取失败原因、持有时长、过期次数。

为什么不是简单 lock()

  • 要控制等待时间、租约、降级、指标；否则一个慢查询能把线程池打满。
  • 锁范围要按业务判断，避免无谓串行。
  • 失败要能降级，不能因为 Redis 抖动整个支付不可用。

设计亮点

  • 注解 + AOP：业务代码只加注解，不侵入锁逻辑。
  • wait/lease/看门狗/降级/指标：不是"一把锁"，是一套可运维的锁。
  • 锁范围可配：按 biz/userId 控制，避免全量串行。

坑

  • 看门狗依赖 Redisson 客户端存活；进程假死可能续期失败。
  • 降级直连 DB 会失去互斥，要靠 DB 乐观锁/唯一键兜底。
  • 锁粒度太大（全局锁）会成瓶颈；太小（每笔交易）可能无意义。

4. Redis 多实例 + Caffeine

Redis 多实例

  • 在线状态 / 签名 / 房间 / 活动排行 / 活动通用分开。
  • 不同用途的可靠性 / 淘汰策略不同；一次大 Key / 内存打满不能同时影响多个业务。
  • 活动排行用独立实例，避免榜单 ZSet 影响房间在线。

Caffeine

  • 房间在线列表、弹窗、关注、禁言、退房等热点数据本地缓存。
  • 减少 Redis 往返；本地缓存要接受短暂不一致。
  • 更新时删缓存 / 版本号 / 延迟双删。

设计亮点

  • 缓存分层：本地 → Redis → DB。
  • 按用途隔离 Redis，避免互相拖垮。
  • 本地缓存扛热点，Redis 做共享。

坑

  • 本地缓存多实例不一致；关键读要回源 / 版本号。
  • 热点 Key / 大 Key 要拆、要限流、要降级。
  • 缓存击穿 / 雪崩：随机过期、互斥重建、兜底值。

5. 事件驱动房间

litaroom 的 PK / 庆典：

  • PkV1Service.start/end 发 PkV1ExecutionEvent；PkV1ExecutionListener 用 @Async @EventListener 消费，通过 Redis convertAndSend 清缓存。
  • 庆典用 @Timer(delay=3) + KV 游标 + limit 100 增量扫描，多 worker 分工。
  • 状态变更和副作用（缓存清理、消息推送、结算）解耦。

设计亮点

  • 核心状态同步写，副作用异步做；不牺牲正确性。
  • 事件解耦：新增副作用不用改主流程。
  • 游标 worker 避免全表扫描；多 worker 要防重。

坑

  • 事件可能丢/重复：要幂等 / 补偿。
  • 异步失败只记录；重要副作用要重试。
  • 多 worker 并发扫描同一游标要加锁/分片。

6. 峰值治理

活动前

  • 容量评估：QPS / 线程池 / 连接池 / Redis / DB。
  • 压测：入口、聚合接口、榜单、发奖。
  • 预案：限流、降级、开关、扩容。

活动中

  • 并行 Pipeline、缓存、异步化。
  • 非核心模块降级（动画 / 广播 / 非关键榜单）。
  • 监控：RT、错误率、线程池、Redis 命中率、Kafka lag。

活动后

  • 复盘：峰值、瓶颈、故障、改进。
  • 对账：奖励 / 榜单 / 配置。

设计亮点

  • 分层扛：入口限流 → 聚合并行 → 缓存 → 异步 → 降级。
  • 开关化：非核心功能随时关。
  • 可观测：RT/错误/线程池/Redis/Kafka 全看。

7. 失败模式

失败点 后果 兜底
捕鱼并发扣血 重复击杀 / 超杀 条件更新 + 唯一索引
溢出递归过深 打穿很多鱼 / 慢 深度限制 + 异步
宝箱多级结算重复 重复发奖 orderNo_level + Redis 标记
余额锁过期 并发写余额 看门狗 + DB 兜底
缓存击穿 DB 被打穿 互斥重建 + 兜底
事件重复消费 重复副作用 消费幂等
线程池打满 聚合接口超时 隔离 + 限流 + 降级
Kafka 积压 结算延迟 监控 lag + 扩容

8. 设计亮点总结

  1. 状态机 + 条件更新：捕鱼 ALIVE→CAUGHT、核销 ACTIVE→USED，用影响行数抢处理权。
  2. 唯一索引：一房间一活鱼、一流水一次发放，数据库兜底。
  3. 多级幂等：orderNo_level 支持一笔流水跨多级。
  4. 可运维的锁：Redisson wait/lease/看门狗/降级/指标，不是裸 lock()。
  5. 缓存分层：Caffeine + Redis 多实例，按用途隔离。
  6. 事件驱动：核心同步、副作用异步，事件解耦。
  7. 峰值治理：限流、降级、开关、压测、监控。
  8. 失败可补偿：Redis 标记失败删、奖励回收队列、对账。

9. 边界 / 坑

  • 锁 TTL / 看门狗 / 降级直连 DB 都有边界；不能把一致性全押在锁上。
  • 本地缓存多实例不一致；关键读要回源。
  • 热点 Key / 大 Key 要拆、限流、降级。
  • 事件可能丢/重复；消费方要幂等。
  • 线程池共享会互相拖垮；活动峰值要隔离。
  • 捕鱼溢出递归要限深；否则大额礼物打穿很多鱼。

10. 面试怎么讲

30 秒版

活动高并发靠组合：捕鱼用条件更新 + 唯一索引 + orderNo_depth，宝箱用唯一键 + 状态机 + Redis 标记，余额用 Redisson 单写者锁，缓存用 Caffeine + Redis 多实例，房间用事件驱动解耦；峰值再靠限流、降级、开关、压测。

2 分钟版

捕鱼是状态机：扣血用 WHERE status='ALIVE' 条件更新，捕捞再抢一次处理权，刷鱼靠唯一索引，溢出伤害用 orderNo_depth 保幂等，死锁重查。宝箱多级结算用 orderNo_level 和状态机，Redis 标记防重、失败删标记。余额变更用 Redisson 锁，wait/lease/看门狗，失败 fail-fast 或降级 DB。缓存本地 + Redis 多实例，按用途隔离。房间用领域事件解耦缓存清理/消息推送，庆典用游标 worker 增量结算。

追问：为什么不用分布式锁？

捕鱼用条件更新 + 唯一索引已经能抢处理权，锁增加失败点；余额才需要锁，因为要保护多步操作。

追问：这个设计有什么风险？

锁 TTL/看门狗、缓存一致性、热点 Key、事件重复、线程池隔离、溢出递归深度；都要监控和兜底。

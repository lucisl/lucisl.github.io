## 一句话

活动高并发不是"加机器"，是**状态机 + 条件更新 + 唯一索引 + 锁 + 缓存分层 + 事件驱动**一起用，保证不重、不丢、不拖垮。

---

## 1. 捕鱼：条件更新 + 唯一索引 + 溢出伤害

**场景**

- 一个房间一条活鱼，用户送礼打鱼；鱼血归零后结算，溢出伤害继续打新鱼。

**并发点**

- 多个用户同时打同一条鱼。
- 鱼死瞬间多个请求同时触发结算。
- 一条鱼死后，剩余伤害要打新鱼。

**解法**

- 扣血：`UPDATE ... WHERE id=? AND status='ALIVE'`，影响行数=0 放弃。
- 捕捞：再用 `WHERE status='ALIVE'` 抢"捕捞处理权"，只有一个请求能成功。
- 刷鱼：唯一索引保证一房间一活鱼；`DuplicateKey` / `Deadlock` 后重查。
- 溢出：递归打新鱼，`orderNo` 加 `_depth` 后缀，保证多条鱼流水幂等。
- 异步：血量变化 / 广播用 `CompletableFuture`，失败不影响主流程。

**面试点**

- 为什么不用分布式锁：条件更新 + 唯一索引已经够，锁增加失败点。
- 死锁是预期：捕获后重查，不当作系统错误。

## 2. 宝箱 / 赐福：唯一键 + 状态机

**宝箱**

- 奖励记录先 insert，唯一键冲突 = 已处理。
- `PENDING → SUCCESS / FAILED`；失败可重试。
- 多级结算：`orderNo + "_" + level`。
- 结算标记 Redis 防重；失败删标记，允许补偿。

**赐福券**

- GET 流水 `trans_no = order_no`；USE 流水 `trans_no = 批次号`。
- 核销 `UPDATE ... WHERE status='ACTIVE'` 单行原子。
- 发放在本地事务内：流水 + 券一起成功 / 失败。

**面试点**

- 唯一键是幂等闸门，不是"先查再写"。
- 状态机让失败可重试、成功不可重复。

## 3. 余额单写者锁

`lita-payment` 的 `UserBalanceLockAspect`：

- `@UserBalanceLock` + Redisson `RLock`。
- `tryLock(waitMs, leaseMs)`；`leaseMs<=0` 用看门狗续期。
- 获取失败：`failFast` 抛"系统繁忙"，否则降级直连 DB。
- 释放判断 `isHeldByCurrentThread()`；过期 / 释放失败记指标。
- 按 `biz + userId` 判断是否在锁范围，不是所有交易都加锁。

**为什么不是简单 `lock()`**

- 要控制等待时间、租约、降级、指标；否则一个慢查询能把线程池打满。
- 锁范围要按业务判断，避免无谓串行。

## 4. Redis 多实例 + Caffeine

**Redis 多实例**

- 在线状态 / 签名 / 房间 / 活动排行 / 活动通用分开。
- 不同用途的可靠性 / 淘汰策略不同；一次大 Key / 内存打满不能同时影响多个业务。

**Caffeine**

- 房间在线列表、弹窗、关注、禁言、退房等热点数据本地缓存。
- 减少 Redis 往返；本地缓存要接受短暂不一致。
- 更新时删缓存 / 版本号 / 延迟双删。

**面试点**

- 缓存分层：本地 → Redis → DB。
- 热点 Key / 大 Key 要拆、要限流、要降级。

## 5. 事件驱动房间

`litaroom` 的 PK / 庆典：

- `PkV1Service.start/end` 发 `PkV1ExecutionEvent`；`PkV1ExecutionListener` 用 `@Async @EventListener` 消费，通过 Redis `convertAndSend` 清缓存。
- 庆典用 `@Timer(delay=3)` + KV 游标 + `limit 100` 增量扫描，多 worker 分工。
- 状态变更和副作用（缓存清理、消息推送、结算）解耦。

**面试点**

- 事件驱动不是"全异步"：核心状态仍同步写，副作用异步。
- 游标 worker 避免全表扫描；多 worker 要防重。

## 6. 峰值治理

**活动前**

- 容量评估：QPS / 线程池 / 连接池 / Redis / DB。
- 压测：入口、聚合接口、榜单、发奖。
- 预案：限流、降级、开关、扩容。

**活动中**

- 并行 Pipeline、缓存、异步化。
- 非核心模块降级（动画 / 广播 / 非关键榜单）。
- 监控：RT、错误率、线程池、Redis 命中率、Kafka lag。

**活动后**

- 复盘：峰值、瓶颈、故障、改进。
- 对账：奖励 / 榜单 / 配置。

## 7. 面试怎么讲

**"活动峰值怎么扛？"**

> 先容量评估 + 压测，再分层扛：聚合接口 Pipeline 并行 + 单模块故障隔离，热点数据本地缓存 + Redis 多实例，非核心功能降级、入口限流；活动前演练，活动后复盘。

**"捕鱼并发怎么处理？"**

> 条件更新抢处理权，唯一索引防重复刷鱼，溢出伤害用 `orderNo_depth` 保幂等，死锁 / 唯一键冲突重查兜底。

**"余额变更怎么保证单写者？"**

> Redisson 锁 + wait/lease/看门狗，失败 fail-fast 或降级 DB；按 biz+userId 控制锁范围，带指标。

**"这个设计有什么风险？"**

> 锁 TTL / 看门狗、缓存一致性、热点 Key、线程池隔离、Kafka 重复消费；都要有监控和兜底。

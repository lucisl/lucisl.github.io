INTERVIEW / AI HIGHLIGHTS

AI 落地亮点

WorkHub 里真正有技术含量的 7 个 AI 落地设计。

一句话总览

WorkHub 的 AI 落地不是"接个大模型 API"，而是把 AI 做成研发流程里的执行角色：有状态、有工具、有权限、有评测、有降级。

下面 7 个点，是项目里真正有技术含量、也最容易被面试追问的地方。

1. Agent 运行时：AI 不是聊天框，是有状态的执行者

做了什么

  • 任务有完整状态机：等待中（待分配 / 待接受 / 待反馈 / 待继续 / 待申请验收 / 待验收）→ 进行中 → 已结束（完成 / 拒绝 / 失败 / 取消）。
  • AI 机器人接任务后，通过 Executor（执行器）会话 执行；会话支持 prompt 队列、interrupt、提问/答复、断线重连。
  • executor-bridge 把 kiro / codex / claude-code 统一成 HTTP + SSE；opencode 直连，平台不绑死一个内核。
  • 长任务用 wakeup（定时唤醒）：等待人工确认、工单审批、脚本结果时，AI 自己设置多久后回来，不占执行容量。

技术难点

  • 会话终态有粘性：必须用"本轮用户消息时间"判断终态是否新鲜，不能只看进程/连接状态。
  • prompt 必须按会话串行：bridge 做 per-session 队列，平台不维护发送队列。
  • 任务成功 ≠ 会话成功：会话成功后还要显式"申请验收"，避免 AI 自己说完成。

面试怎么讲

我们不是让 AI 聊一句就结束，而是给它一个任务状态机和执行器会话：能接单、能提问、能返工、能验收，断线能恢复，长任务能唤醒。

2. 工具生态：102 + 6 + 31 个 MCP 工具

做了什么

  • lita-work：102 个平台工具，覆盖需求 / 迭代 / 文档 / 知识 / 脚本 / 缺陷 / 反馈 / 灵感 / GitHub / 任务 / 工单 / 飞书。
  • lita-bots：6 个工具，把平台机器人当 Sub-agent（子智能体） 调用，支持多轮、提问、中断、断线找回。
  • lita-proxy：31 个运维工具，覆盖 MySQL / ClickHouse / ODPS / Redis / SLS / Nacos / XXL-JOB / Firebase / GitHub PR / 工单。

技术难点

  • 工具不是越多越好：要按身份、作用域、读写权限拆，否则 AI 很容易越权。
  • 生产写不能直接给 AI：生产只读，测试可写，生产写必须走工单 + 人工审批。
  • 工具结果要可审计：谁在什么时候调用了什么、参数是什么、结果是什么。

面试怎么讲

我们把平台能力拆成细粒度 MCP 工具，按机器人身份鉴权；AI 能查、能改测试环境、能建 PR，但生产写必须走审批。工具生态是 AI 落地的手脚，权限是刹车。

3. 反馈闭环：飞书群话题 → 平台 feedback → AI 处理

做了什么

  • 飞书反馈群里，一个 Topic/Thread（话题/线程） 自动收录为一条平台 feedback；用 root_id 归并同话题消息，防误建。
  • 首帖自动创建任务定义 ID=8「用户反馈处理」，AI 读 feedback + 跟帖，判断真实性 / 类型 / 紧急度，能处理就处理，不能处理给结论和转派建议。
  • 群策略支持 smart（AI 判断是否回复）、at（仅 @）、record（仅记录）、feedback（反馈采集）。
  • 智能反馈按 5 秒 / 10 条 Batch（批处理），AI 判定不需要回复时输出 [不回复]，避免刷屏。

技术难点

  • 重复消息：按消息 id / topic root 去重，机器人自身消息不回传，防回声。
  • 群会话隔离：每个群 / 话题独立 session，不和私聊混。
  • 人在回路：AI 判断错了要能转人工，不能把反馈直接关掉。

面试怎么讲

用户反馈群最怕刷屏和漏看。我们让平台确定性地把话题收成 feedback，再让 AI 做分诊：真 BUG 还是建议、紧急不紧急、归哪个项目；能处理就回复，不能处理给结论和转派。群策略可配，智能模式会主动 [不回复]。

4. 线上巡检：活动 PK 数据的定时抽检

做了什么

  • checks + schedules：把检查脚本登记成 .check.ts，用 cron 定时跑。
  • PK 活动按阶段拆检查：day-3 ~ day-7、phrase-4、final。
  • 检查内容：mod_common_round 结算状态 status=200、活动 API 拉前 N 名榜单、奖励配置文档解析、mod_common_award_record 发奖记录，按 rank 区间 / 奖励类型 / 发放对象核对差异。
  • 运行结果有 SSE 实时输出、运行历史、成功 / 失败统计；异常可转缺陷 / 工单。

技术难点

  • 只读生产：只读数据源 / 只读事务、带 LIMIT、超时控制，检查脚本不写业务库。
  • 确定性：检查逻辑是脚本，不是让 AI 自由发挥；AI 可以生成 / 修改脚本、看结果、转工单。
  • 活动阶段多：每个阶段的时间、榜单、奖励配置都不同，脚本要按大区和阶段参数化。

面试怎么讲

活动上线后最怕奖励发错、榜单不对。我们把每个阶段的检查写成脚本，定时在生产只读库 + 活动 API 上抽检，自动输出差异。AI 不直接改生产，但可以帮我们生成检查、看结果、转缺陷。

5. RAG：PGVector + 全文 + RRF

做了什么

  • 知识树：knowledge_nodes 目录 / 文章，knowledge_chunks 按 Markdown 标题切片 + Embedding。
  • 检索：全文 + 向量 Hybrid Retrieval（混合检索），用 RRF（倒数排名融合） 融合两路结果。
  • 向量不可用时降级全文；低相似纯向量候选不进入 RRF；PROJECT_KNOWLEDGE_SEARCH_VECTOR_MIN_SIMILARITY 默认 0.65。
  • Embedding 队列异步生成，维度默认 1024。

技术难点

  • 全文和向量分数尺度不同，不能直接加权；RRF 只看排名，稳定。
  • chunk 太大召回不准，太小上下文断裂；按标题切 + metadata。
  • 权限：chunk 带 ACL / tenant，检索前过滤，引用时校验。

面试怎么讲

我们不是裸向量库：全文和向量各召回一路，RRF 融合；低相似纯向量结果过滤掉，向量服务挂了降级全文。知识库解决的是"AI 回答有没有依据"，不是"能不能搜到一段话"。

6. Eval：给 AI 做"可回归的考试"

做了什么

  • 测试集 eval_suite → 用例 eval_case → 要点 eval_case_point；测试集分 train / validation。
  • 批次 eval_run → 评估项 eval_run_item（用例 × 重复）；每个评估项创建一个 is_eval=1 的任务，在独立沙箱执行。
  • 判定 eval_judgement：评估机器人按 Rubric（评分要点） 逐条判 hit=0 / 0.5 / 1，必须给 Evidence（证据） 原文摘录。
  • 平台做 Evidence Validation（证据校验）：证据必须是交付内容子串（规范化后长度 ≥4），不合法直接判 0。
  • 算分：score = round(100 × Σ(w×h) / Σw)；必需项全命中且分数 ≥ 阈值（默认 80）才通过；失败给一次 Rework（返工）。

技术难点

  • Judge 会瞎判：用证据校验把"裁判幻觉"压下去。
  • 沙箱隔离：复制真实工位，剔除 docs/、.env、MCP 配置；注入短效 eval token；独立 HOME。
  • 并发与恢复：全局 5、判定 3、单批次 3、单项上限 200；tick 每 2 秒推进；失败续跑 30s / 3min；判定最多 3 次。

面试怎么讲

我们给 AI 做了可回归的评测：测试集、Rubric、LLM-as-judge，但 judge 必须引用交付原文，平台校验证据，证据不合法直接判 0；必需项全命中且过阈值才算通过，失败给一次返工。整个执行在沙箱里，权限用 eval token + shield 限制。

7. 模型降级：主备 + 冷却 + 同会话续跑

做了什么

  • 主模型 + 备用模型；识别 429 / 配额 / 余额 / Token 用尽等限额错误。
  • 按 executor + provider + model 共享冷却 30 分钟；同执行器共用该模型的新会话直接用备用。
  • 同 session switchModel + continue prompt 续跑；每轮最多切一次；备用也失败走原失败流程。
  • 上下文超长 / max tokens 这类非限额错误不触发降级，因为换模型解决不了。

技术难点

  • 冷却状态在进程内，重启清空；多实例后端不共享（可升级 Redis）。
  • 切换后续跑可能重复工具调用，需要工具幂等。
  • 备用模型能力可能更差，需要评测 / 人工接管。

面试怎么讲

主模型 429 / 配额 / 余额不足时，先按 executor + provider + model 标记冷却 30 分钟，然后在同一 session 里切到备用模型，用 continue prompt 续跑，每轮最多切一次；上下文超长不切，因为换模型解决不了。备用也限额就回到原失败流程。

8. Guardrails：AI 能动手，但边界清楚

做了什么

  • Eval Token（评测令牌）：JWT 30 分钟，身份 = 被测 / 评估机器人，评估项结束吊销。
  • Eval Shield（评测拦截）：拦截写操作、子任务、需求方动作、越权任务；判定令牌只能调 2 个判定工具。
  • 沙箱：复制工位时剔除凭据 / MCP 配置，注入评估令牌，独立 HOME；bridge 校验沙箱必须在执行器工作区内。
  • 生产安全：生产只读、测试可写、生产写走工单 + 人工审批；敏感列只写不回显；审计不落原始 Token / PAT。

面试怎么讲

AI 能动手，但边界很清楚：工具层用 MCP policy 和最小权限；执行层用 eval token + shield 拦写 / 子任务 / 越权；业务层生产只读、写操作走工单 + 人工审批。所有调用留审计，不落原始 Token。

9. 边界：哪些不是 WorkHub 做的

  • 不是全自动交付：只到 PR，不自动合并；生产写要审批。
  • 不是 AI 直接修生产：巡检脚本只读，异常转缺陷 / 工单。
  • 没有 fine-tuning / vLLM / GraphRAG：不要为了匹配 JD 硬说。
  • work 仓库如果你 0 提交：说"基于 / 推动 / 落地 WorkHub"，不要说"我开发了 WorkHub"。

面试 30 秒总览

WorkHub 把 AI 做成研发流程里的执行角色：任务有状态机，执行有 Agent 运行时，工具有 MCP，反馈有飞书闭环，线上有定时巡检，知识有 RAG，质量有 Eval，模型有限额降级，权限有 Guardrails。它不是"接了个大模型"，是把 AI 放进了可运行、可审计、可回归的工程体系里。

## 一、项目定位

<strong>WorkHub 是一个以 AI 为中心的项目管理平台</strong>。传统平台把 AI 当辅助工具，它把 AI 机器人当成 「员工」：有工位、有角色、有模型、有权限，可以接任务、执行、交付、被验收，也会提问、卡住、失败。

使用方是某互联网公司的研发、测试、产品与运营团队。核心场景是： 需求从外部表格单向同步进来 → 排进迭代 → 拆成交付任务派给机器人 → 机器人在自己的工位里执行 → 产出交付文档 → 人工验收 → 需要时走工单、提测和缺陷闭环。

平台同时承担一个不那么显眼的职责<strong>：把「AI 执行」这件不可靠的事，变成可运营、可审计、可回滚的系统行为</strong>。 这比做一个聊天框难得多。

## 二、规模与开发方式

| 维度 | 数据 |
| --- | --- |
| 代码量 | 后端约 12.8 万行 / 581 个文件；前端约 5 万行 / 148 个文件；独立执行器桥约 2.2 千行 |
| 数据模型 | 69 个实体，93 个数据库迁移 |
| 接口层 | 52 个控制器，113 个 MCP 工具注册 |
| 前端页面 | 67 个页面组件 |
| 测试 | 132 个单测文件 |
| 提交历史 | 278 个提交，约 3 个月 |
| 贡献结构 | 主作者约 96%，AI 机器人 22 个提交，其余来自团队 |

这个比例说明了开发方式<strong>：人负责架构、边界、验收和规范，AI 负责大量编码与重复性改造</strong>。 为了让 AI 能持续参与而不跑偏，项目里有一份「跨模块不变量」文档（`AGENTS.md`）， 只记录稳定约定，不复制页面和字段清单——它既是人的设计备忘，也是 AI 的约束文件。

## 三、架构全景

```diagram
┌──────────── 浏览器（React 19 + 组件库 + Tailwind）────────────┐
│ 需求 / 迭代 / 任务 / 工单 / 知识库 / 机器人 / 话题   SSE 实时流    │
└───────────────┬────────────────────────────────────────────────┘
                │ /api （HttpOnly JWT Cookie + 全局鉴权守卫）
┌───────────────▼────────────────────────────────────────────────┐
│ NestJS 后端（strict TS + TypeORM + PostgreSQL + pgvector）       │
│                                                                 │
│  领域：需求 → 迭代项 → 任务 → 工单 → 提测 → 缺陷   话题   知识库   │
│                                                                 │
│  执行：统一执行器接口 ─┬─ 执行内核 A（直连 HTTP + SSE）           │
│                        └─ 执行器桥（多内核：B / C / D）           │
│                                                                 │
│  身份：用户 / 真人机器人 / AI 机器人 / 个人助理 / 公共 Agent       │
│  开放：平台工具 MCP（100+ 工具）+ 调用机器人 MCP                  │
└───────────────┬────────────────────────────────────────────────┘
                │
   ┌────────────┼─────────────┬──────────────┐
   ▼            ▼             ▼              ▼
 即时通讯平台   资源代理 MCP    代码托管        移动端自动化
 登录/文档/群   数据库/缓存/   凭证网关        设备远程运行
 话题/卡片     配置/日志      短租凭证
```

四个关键边界：

- <strong>领域与执行分离</strong>：任务状态机不关心底层是哪个执行内核，只依赖统一接口。
- <strong>平台与工位分离</strong>：机器人的人格、技能、规范、MCP 配置都落在工位目录里，平台只负责生成和注入。
- <strong>人与 AI 同权</strong>：同一套接口既服务网页用户，也服务机器人令牌，不为 AI 单独维护一套 API。
- <strong>凭据不出平台</strong>：代码托管、数据库、缓存等敏感凭据由网关代持，机器人只拿短期凭证。

## 四、业务主链路

一条需求从进入到关闭，要穿过六个状态域：

1.  <strong>需求池</strong>：从外部表格单向同步，也支持平台内新建；状态是<strong>读时推导</strong>，不落库。
2.  <strong>迭代</strong>：分常驻快速通道、每周通道、特殊通道三类，标识按自然周自动生成。
3.  <strong>迭代项</strong>：独立于需求的交付单元，成员统一用「机器人」表示，负责人和需求方自动列入。
4.  <strong>交付任务</strong>：完整状态机（待分配 → 执行中 → 待验收 → 完成），支持提问、答复、返工、取消。
5.  <strong>工单</strong>：可配置工作流，节点类型覆盖操作、审批、验收、条件判断和群消息。
6.  <strong>提测与缺陷</strong>：批量提测自动建单并通知；缺陷可被脚本回归结果自动关闭。

横切能力有三块<strong>：话题</strong>（挂在任意主体下的讨论串，与即时通讯群双向同步）、 <strong>知识库</strong>（全文 + 向量混合检索）<strong>、机器人体系</strong>（工位、模型、技能、规范、MCP、定时唤醒）。

## 五、六个关键设计决策

### 1\. 把 Agent 当一等公民

每个实体都有面向机器的 Markdown 视图，带 YAML 前置信息，既读又能写；机器人令牌与网页会话平权。 结果是一套接口同时服务人和 AI，不用维护两套 API，也让「让 AI 自己查资料、自己操作」成为默认能力。

> <strong>代价</strong>：需要严格的身份模型和权限校验，否则 AI 会越权。

### 2\. 工位即上下文

机器人的「人格」不是数据库里一段 prompt，而是工位目录里的角色文档、技能目录、规范目录和 MCP 声明。 目录按执行内核对齐设计：平台只维护唯一的「源」，再按内核镜像出适配物。换执行内核不用改业务代码。

> <strong>代价</strong>：工位初始化、令牌落盘、工作区边界都要单独设计。

### 3\. 执行器抽象

平台只依赖统一执行器接口：会话、投递、中断、事件流、提问。一个内核直连，其他内核由独立桥接服务承载。 事件中心按执行器复用一条事件流，引用归零后延迟断开，断线自动重连。

> <strong>代价</strong>：不同内核的能力差异要逐个适配，且必须在协议层写清楚。

### 4\. 可靠异步

所有长任务都是「立即返回 + 快照/增量推送 + 可恢复」：收件箱、循环恢复、2/10/30 分钟退避、 幂等键、定时唤醒、外部事件回调。会话成功不等于任务完成，执行方必须显式申请验收。

> <strong>代价</strong>：状态机和事件链路复杂度显著上升，排查成本高。

### 5\. 凭据最小暴露

代码托管令牌、数据库口令、第三方密钥只由服务端持有；机器人拿短租凭证，平台工具令牌不进提示词、日志和响应； 工作区边界禁止读写工位之外的路径。

> <strong>代价</strong>：AI 越能干，越要假设它会被诱导，安全设计必须前置。

### 6\. 规约先行

`AGENTS.md` 记录跨模块稳定约定与业务不变量；另有界面规范、执行器协议、工位目录规范。 文档写给「人和 AI 都能读」的格式，成为可执行的约束，而不是过期的说明。

> <strong>代价</strong>：约定变更时必须同步文档，否则规范会反过来误导 AI。

## 七、能力提升

### 架构与领域建模

把一条真实业务链拆成 69 个实体、93 次渐进迁移，而不是一次性设计。学会区分推导值与落库值、 软引用与物理外键、状态机守卫与展示状态。

### 异步与可靠性

事件驱动、幂等三件套（唯一键、状态守卫、乐观更新）、退避重试与恢复、实时流的快照 + 增量 + 晚订阅。 这些是「系统能不能长期跑」的分水岭。

### AI Agent 工程

MCP 工具设计（参数 schema、错误语义、权限校验、审计）、上下文工程（角色/技能/规范分层注入）、 会话隔离与生命周期、多模型容错与备用切换、多执行内核适配。

### 平台集成

即时通讯平台的登录、长连接、卡片、话题双向同步、文档与多维表格转 Markdown； 代码托管的事件与凭证网关；执行内核的 HTTP + SSE 协议。

### 数据与检索

PostgreSQL 高级特性：生成列 + GIN 索引、向量列、部分唯一索引、时区规范； 混合检索的融合排序、相似度阈值与降级策略。

### 安全与权限

四层权限模型（登录、角色、业务身份、机器人权限档位）、令牌体系与负 ID 隔离、 工作区边界、审计与运维止血开关。

### 产品与协作

设计「人 + AI 混合团队」的流程：谁能接受任务、谁能验收、失败了怎么升级、什么时候提醒。 把模糊需求落成可执行的规约与模板。

### 工程文档

写给 AI 看的规约：只记不变量、不记快照；变更即同步。文档从「给人看的说明」变成「可执行的约束」。

## 八、客观局限

- <strong>知识集中</strong>：绝大多数提交来自一人，模块间耦合较深，新人上手成本高。
- <strong>测试不均</strong>：单测数量不少，但任务状态机、即时通讯长连接、执行器事件等核心链路覆盖不足。
- <strong>传输安全</strong>：内网部署长期使用明文 HTTP，令牌在网络上明文传输，是明确的待改进项。
- <strong>权限边界</strong>：部分管理接口历史上依赖前端隐藏按钮，服务端校验需要系统性补齐。
- <strong>复杂度</strong>：实体与迁移数量大，部分功能（占位模块、多内核）尚未经过生产验证。
- <strong>外部依赖多</strong>：即时通讯、资源代理、执行内核、设备代理任一不可用都会影响链路。

## 九、可迁移的方法论

1.  <strong>先写不变量，再写代码</strong>。只记稳定约定的文档不会腐烂，也能约束 AI。
2.  <strong>用协议隔离易变</strong>。执行器、MCP、内核适配物，本质都是把变化关在接口后面。
3.  <strong>长任务三件套</strong>。立即返回、事件推送、可恢复——不要同步等。
4.  <strong>幂等 + 退避</strong>。AI 执行一定会失败，系统要能重来而不重复。
5.  <strong>凭据不进 AI 上下文</strong>。短期凭证 + 网关代持，是 AI 系统的基本安全线。
6.  <strong>开关优于完美</strong>。止血开关让「上线出错」变成「可以暂停」，这是运营级系统的标志。

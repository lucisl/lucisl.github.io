这个域解决什么问题

活动是平台拉收、拉活、拉留存的主要手段：把签到、任务、PK、榜单、抽奖、召回、节日主题这些玩法，组织成有目标、有奖励、有周期的运营动作。

Lita 的活动分三类（来自 active-main/README.md）：

  • 运营活动：周年庆、节日、用户召回、邀请等
  • 产品活动：礼物活动、荣耀等级、游戏排行榜等
  • 游戏活动：游戏任务、游戏成就、游戏段位等

代码怎么组织

active-main：一活动一目录

business/
  dailycheck/       # 每日签到
  invite/           # 邀请
  userrecall202508/ # 用户召回
  pk/               # PK
  roomrank2026/     # 房间榜
  monopoly/         # 大富翁
  ...
dispatch/           # 活动分发器
component/          # 数据源、Redis、安全等全局配置

README 里有一份明确的「已废弃包」清单：全局的 controller、consumer、cron、dispatch/bizdispatcher 正在迁入各个活动自己的目录。理解这条改造方向，就能理解 v3 为什么是现在这样。

active-v3：五层结构

business/     # 业务编排
active/       # 每个活动一个子包（home / pk / halloween / room / giftRank / magicbox …）
module/       # 可复用模块
coordinator/  # 协调器
core/         # 基础设施

活动内部自带接口、消费者、定时任务，避免不同活动互相干扰；支持 GraalVM Native Image，适合活动期弹性扩容。

一次活动的生命周期

配置活动 → 入口 / 报名 → 任务 / 签到 / 抽奖 → 榜单累计 → 结算 → 发奖 / 补发 → 数据回流。

几个关键点：

  • 配置与代码分离：运营改配置即可调整档位、奖励、时间，不用发版
  • 榜单：通常用 Redis ZSet 实时累计，结算落库并补发
  • 补发与对账：活动结束必须有补发机制，避免漏奖
  • 数据：活动数据进 lita_active，分析走数仓

技术点与坑

  • 活动即模块：新活动复制一个目录，自带接口 / 消费者 / 定时任务
  • Redis 纪律：active-main README 要求统一使用全局 Redis 配置，禁止单独配置
  • 接口收敛：v3 的 Controller 从 41 降到 13，统一入口分发
  • Native Image：v3 支持，冷启动更快，适合活动峰值
  • 新老并存：lita-active 仍在跑，定位一个活动要三处搜

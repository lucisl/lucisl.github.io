PROJECT HANDBOOK / 001

AI 工作中心

WorkHub

让 AI 机器人像同事一样接任务、干活、交付，而不是一个聊天窗口。

  • 周期约 3 个月
  • 规模约 18 万行
  • 数据模型69 个实体
  • MCP 工具113 个
  • 协作方式单人主导 + AI

一、项目定位

WorkHub 是一个以 AI 为中心的项目管理平台。传统平台把 AI 当辅助工具，它把 AI 机器人当成 「员工」：有工位、有角色、有模型、有权限，可以接任务、执行、交付、被验收，也会提问、卡住、失败。

使用方是某互联网公司的研发、测试、产品与运营团队。核心场景是： 需求从外部表格单向同步进来 → 排进迭代 → 拆成交付任务派给机器人 → 机器人在自己的工位里执行 → 产出交付文档 → 人工验收 → 需要时走工单、提测和缺陷闭环。

平台同时承担一个不那么显眼的职责：把「AI 执行」这件不可靠的事，变成可运营、可审计、可回滚的系统行为。 这比做一个聊天框难得多。

这个比例说明了开发方式：人负责架构、边界、验收和规范，AI 负责大量编码与重复性改造。 为了让 AI 能持续参与而不跑偏，项目里有一份「跨模块不变量」文档（AGENTS.md）， 只记录稳定约定，不复制页面和字段清单——它既是人的设计备忘，也是 AI 的约束文件。

四个关键边界：

  • 领域与执行分离：任务状态机不关心底层是哪个执行内核，只依赖统一接口。
  • 平台与工位分离：机器人的人格、技能、规范、MCP 配置都落在工位目录里，平台只负责生成和注入。
  • 人与 AI 同权：同一套接口既服务网页用户，也服务机器人令牌，不为 AI 单独维护一套 API。
  • 凭据不出平台：代码托管、数据库、缓存等敏感凭据由网关代持，机器人只拿短期凭证。

四、业务主链路

一条需求从进入到关闭，要穿过六个状态域：

  1. 需求池：从外部表格单向同步，也支持平台内新建；状态是读时推导，不落库。
  2. 迭代：分常驻快速通道、每周通道、特殊通道三类，标识按自然周自动生成。
  3. 迭代项：独立于需求的交付单元，成员统一用「机器人」表示，负责人和需求方自动列入。
  4. 交付任务：完整状态机（待分配 → 执行中 → 待验收 → 完成），支持提问、答复、返工、取消。
  5. 工单：可配置工作流，节点类型覆盖操作、审批、验收、条件判断和群消息。
  6. 提测与缺陷：批量提测自动建单并通知；缺陷可被脚本回归结果自动关闭。

横切能力有三块：话题（挂在任意主体下的讨论串，与即时通讯群双向同步）、 知识库（全文 + 向量混合检索）、机器人体系（工位、模型、技能、规范、MCP、定时唤醒）。

五、六个关键设计决策

1. 把 Agent 当一等公民

每个实体都有面向机器的 Markdown 视图，带 YAML 前置信息，既读又能写；机器人令牌与网页会话平权。 结果是一套接口同时服务人和 AI，不用维护两套 API，也让「让 AI 自己查资料、自己操作」成为默认能力。

代价：需要严格的身份模型和权限校验，否则 AI 会越权。

2. 工位即上下文

机器人的「人格」不是数据库里一段 prompt，而是工位目录里的角色文档、技能目录、规范目录和 MCP 声明。 目录按执行内核对齐设计：平台只维护唯一的「源」，再按内核镜像出适配物。换执行内核不用改业务代码。

代价：工位初始化、令牌落盘、工作区边界都要单独设计。

3. 执行器抽象

平台只依赖统一执行器接口：会话、投递、中断、事件流、提问。一个内核直连，其他内核由独立桥接服务承载。 事件中心按执行器复用一条事件流，引用归零后延迟断开，断线自动重连。

代价：不同内核的能力差异要逐个适配，且必须在协议层写清楚。

4. 可靠异步

所有长任务都是「立即返回 + 快照/增量推送 + 可恢复」：收件箱、循环恢复、2/10/30 分钟退避、 幂等键、定时唤醒、外部事件回调。会话成功不等于任务完成，执行方必须显式申请验收。

代价：状态机和事件链路复杂度显著上升，排查成本高。

5. 凭据最小暴露

代码托管令牌、数据库口令、第三方密钥只由服务端持有；机器人拿短租凭证，平台工具令牌不进提示词、日志和响应； 工作区边界禁止读写工位之外的路径。

代价：AI 越能干，越要假设它会被诱导，安全设计必须前置。

6. 规约先行

AGENTS.md 记录跨模块稳定约定与业务不变量；另有界面规范、执行器协议、工位目录规范。 文档写给「人和 AI 都能读」的格式，成为可执行的约束，而不是过期的说明。

代价：约定变更时必须同步文档，否则规范会反过来误导 AI。

七、能力提升

架构与领域建模

把一条真实业务链拆成 69 个实体、93 次渐进迁移，而不是一次性设计。学会区分推导值与落库值、 软引用与物理外键、状态机守卫与展示状态。

异步与可靠性

事件驱动、幂等三件套（唯一键、状态守卫、乐观更新）、退避重试与恢复、实时流的快照 + 增量 + 晚订阅。 这些是「系统能不能长期跑」的分水岭。

AI Agent 工程

MCP 工具设计（参数 schema、错误语义、权限校验、审计）、上下文工程（角色/技能/规范分层注入）、 会话隔离与生命周期、多模型容错与备用切换、多执行内核适配。

平台集成

即时通讯平台的登录、长连接、卡片、话题双向同步、文档与多维表格转 Markdown； 代码托管的事件与凭证网关；执行内核的 HTTP + SSE 协议。

数据与检索

PostgreSQL 高级特性：生成列 + GIN 索引、向量列、部分唯一索引、时区规范； 混合检索的融合排序、相似度阈值与降级策略。

安全与权限

四层权限模型（登录、角色、业务身份、机器人权限档位）、令牌体系与负 ID 隔离、 工作区边界、审计与运维止血开关。

产品与协作

设计「人 + AI 混合团队」的流程：谁能接受任务、谁能验收、失败了怎么升级、什么时候提醒。 把模糊需求落成可执行的规约与模板。

工程文档

写给 AI 看的规约：只记不变量、不记快照；变更即同步。文档从「给人看的说明」变成「可执行的约束」。

八、客观局限

  • 知识集中：绝大多数提交来自一人，模块间耦合较深，新人上手成本高。
  • 测试不均：单测数量不少，但任务状态机、即时通讯长连接、执行器事件等核心链路覆盖不足。
  • 传输安全：内网部署长期使用明文 HTTP，令牌在网络上明文传输，是明确的待改进项。
  • 权限边界：部分管理接口历史上依赖前端隐藏按钮，服务端校验需要系统性补齐。
  • 复杂度：实体与迁移数量大，部分功能（占位模块、多内核）尚未经过生产验证。
  • 外部依赖多：即时通讯、资源代理、执行内核、设备代理任一不可用都会影响链路。

九、可迁移的方法论

  1. 先写不变量，再写代码。只记稳定约定的文档不会腐烂，也能约束 AI。
  2. 用协议隔离易变。执行器、MCP、内核适配物，本质都是把变化关在接口后面。
  3. 长任务三件套。立即返回、事件推送、可恢复——不要同步等。
  4. 幂等 + 退避。AI 执行一定会失败，系统要能重来而不重复。
  5. 凭据不进 AI 上下文。短期凭证 + 网关代持，是 AI 系统的基本安全线。
  6. 开关优于完美。止血开关让「上线出错」变成「可以暂停」，这是运营级系统的标志。
